## Overall assessment

Architecture direction is sound: clean layering (`MeetGistKit` = product
logic/persistence, `app/Sources` = SwiftUI presentation), a deliberately small
two-slot provider abstraction (`Transcriber` / `NotesWriter` in
[Pipeline.swift](../Sources/MeetGistKit/Pipeline.swift)), and unusually good
engineering documentation (`AGENTS.md`, `docs/ARCHITECTURE.md`, explicit
invariants and "known traps"). The offline transcription subsystem in
particular is well engineered (resumable jobs, atomic part writes, config-ID
namespacing, graceful-then-SIGKILL shutdown).

The gap is in implementation discipline: `AppState` has become a god object,
there is significant copy-paste across the three local-runtime managers and
the various subprocess-supervision code paths, and there are several bugs in
the recording/processing flow that can lose user data (an already-paid-for
transcript, or overwrite a previous recording's audio).

**Priority order for another agent to work through:**
1. Fix the data-loss bugs (P0 section) — small, surgical changes.
2. Fix the post-process deadlock and the offline-scan race (also P0).
3. Security/supply-chain fixes (pin Qwen3-ASR revision, move Gemini key off
   the URL).
4. Add CI that actually builds+tests on macOS.
5. Only then: the larger refactors (split AppState, de-stringify providers,
   unify runtime managers) — valuable but not urgent, and easy to get wrong
   without tests in place first.

## P0 — Data-loss / correctness bugs

### 1. Cloud pipeline can lose an already-transcribed transcript
**Where:** [Pipeline.swift:70](../Sources/MeetGistKit/Pipeline.swift#L70) inside
`ComposedPipeline.process`, consumed by
[SessionRecorder.swift:100](../Sources/MeetGistKit/SessionRecorder.swift#L100)
(`MeetingProcessor.process`).

`ComposedPipeline.process` runs `transcriber.transcribe(...)` then
immediately `notesWriter.notes(transcript:...)` in the same function, holding
the transcript only in memory. `MeetingProcessor.process` only writes
`transcript.md` / `polished.md` / `summary.md` **after** `pipeline.process`
returns successfully. If the notes call throws (bad model name, HTTP 429,
network drop) after a transcript that may have taken an hour and real API
spend to produce, the transcript is discarded — nothing is written to disk.

Contrast with the offline path, which writes `transcript.md` as a durable
artifact of `FLOW-3` before notes ever run (per `docs/ARCHITECTURE.md`'s own
stated contract: "`transcript.md`... is the sole canonical input to notes
generation").

**Fix direction:** make cloud transcription honor the same contract — write
`transcript.md` right after `transcriber.transcribe(...)` succeeds, before
calling the notes writer at all. This can be done inside
`ComposedPipeline.process` (needs `sessionDir` write access, which it already
has) or by restructuring `MeetingProcessor.process` to call transcribe and
notes as two separate stages, mirroring how `MeetingProcessor.generateNotes`
already works independently. The second option also collapses the
"stringly-typed dual code path" issue noted in P2 §2.

### 2. Starting a new recording while a cloud process task is still running corrupts state
**Where:** `toggleRecording()` at
[AppState.swift:250](../../app/Sources/AppState.swift#L250) (dispatches to
`startRecording()` for `.idle`, `.error`, **and `.processing`**);
`processCloud`'s task completion sets `self.state = .idle` at
[AppState.swift:360](../../app/Sources/AppState.swift#L360).

`startRecording()` explicitly cancels/stops the **offline** coordinators and
the local-notes task if active (see the `if offlineCoordinator.activeSessionID
!= nil ... else if qwenASRCoordinator ... else if localNotesTaskActive` chain
just above `startRecording`), but it has **no branch for an in-flight cloud
`processTask`**. So: user taps record while a cloud transcribe/notes job is
running → a new `SessionRecorder` starts immediately → later the old cloud
task's completion handler fires and sets `state = .idle`, `status = "Notes
ready."` etc., stomping whatever state the new recording had reached.

**Fix direction:** in `startRecording()`, also cancel `processTask` (and
await it if there's any resource it needs to release) when a cloud job is
in flight, symmetric to the existing offline/local-notes handling. Simpler
alternative: track "is a background job running" as state independent from
recording state (see P1 §1 — this is really a symptom of the same
underlying design problem), so recording can never be shadowed by a
notes-completion callback.

### 3. Session folder name only has minute resolution → can silently overwrite a previous recording
**Where:** [SessionRecorder.swift:20](../Sources/MeetGistKit/SessionRecorder.swift#L20)
(`df.dateFormat = "yyyy-MM-dd-HHmm"`), combined with
[SystemAudioRecorder.start](../Sources/MeetGistKit/Recorder.swift) and
`MicRecorder.start`, both of which do `try? FileManager.default.removeItem(at:
outputURL)` before recording.

Two recordings started in the same minute (same detected meeting title, or
both with no detected title) resolve to the same `sessionDir` name. The
second recording's `start()` deletes the first's `system.m4a`/`mic.m4a`
before writing new ones. Combined with bug #2 above (a stray leftover
recording could still be "active" when a new one starts), the overwrite risk
compounds.

**Fix direction:** include seconds (or a short random/uuid suffix) in the
folder-name stamp, and/or have `SessionRecorder.init` detect an existing
`sessionDir` and disambiguate (append `-2`, `-3`, ...) instead of reusing it.

### 4. Post-process script can deadlock the app forever
**Where:** [PostProcessRunner.swift:27](../../app/Sources/Automation/PostProcessRunner.swift#L27)

```swift
try task.run()
task.waitUntilExit()                 // <-- blocks here
let out = ...stdout.fileHandleForReading.readDataToEndOfFile()...
let err = ...stderr.fileHandleForReading.readDataToEndOfFile()...
```

Calling `waitUntilExit()` before draining the `Pipe`s is a classic deadlock:
if the user's Python script writes more than the pipe buffer (~64KB on
macOS) to stdout or stderr, the child blocks on `write()` because nothing is
reading, and the parent blocks on `waitUntilExit()` waiting for the child to
exit. Neither side can proceed. There is also no timeout, so this can hang
the app's `.processing` state indefinitely (the UI has no way out except
force-quitting the app).

**Fix direction:** read both pipes concurrently with the process running
(e.g. set `readabilityHandler` on each `FileHandle`, or read on background
queues) before/while calling `waitUntilExit()`, and add a timeout that
terminates the process and reports a clear error (mirroring the pattern
already used for Codex CLI in
[CodexCLINotes.swift](../Sources/MeetGistKit/CodexCLINotes.swift) — see
`CodexProcessController`, which already solves the "subprocess might hang"
problem once; reuse or adapt it here rather than writing a third variant).

### 5. `OfflineJobCoordinator.scan()` mutates on-disk state and can race an active job
**Where:** [OfflineJobCoordinator.swift:77-78](../Sources/MeetGistKit/OfflineJobCoordinator.swift#L77-L78)
inside `scanSync`, which calls `store.recover()` for every session folder.

`OfflineJobStore.recover()` (in
[OfflineJobStore.swift](../Sources/MeetGistKit/OfflineJobStore.swift))
deletes `*.tmp` files and rewrites `state.json` for **every** meeting folder
under the output directory, every time `scan()` runs. `scan()` is called
from several places that have nothing to do with the session currently being
transcribed — e.g. `moveMeetingToTrash` calls
`offlineCoordinator.scan(outputDir:)` and `qwenASRCoordinator.scan(...)`
right after deleting an unrelated meeting
([AppState.swift](../../app/Sources/AppState.swift), see
`moveMeetingToTrash`). Both coordinators also scan independently and
concurrently (`Task.detached` from two different objects) with no
coordination.

If `scan()` runs for the session folder that has an actively-running worker
(state transitioning between `pending`/`transcribing`, tmp part files being
written), `recover()` could delete a tmp file the worker is mid-write on, or
overwrite `state.json` with a stale recovered view right as the coordinator
is also writing progress to it. Low probability but real, since nothing
currently excludes the active session from a scan.

**Fix direction:** in `scanSync`, skip (or have the caller skip) the
`sessionID` that matches `activeSessionID` on either coordinator. Longer
term, `recover()` doing writes as a side effect of what's conceptually a
read-only "rebuild the in-memory job list" operation is itself surprising —
consider splitting "read + repair" from "list".

### 6. Partial recording start leaves ScreenCaptureKit stream running
**Where:** [SessionRecorder.swift:31-32](../Sources/MeetGistKit/SessionRecorder.swift#L31-L32)

```swift
public func start() async throws {
    try await system.start(outputURL: systemURL)
    try mic.start(outputURL: micURL)   // if this throws, system stream keeps running
}
```

If `system.start` succeeds but `mic.start` throws, `SessionRecorder.start()`
propagates the error and `AppState.startRecording()`'s catch block sets
`state = .error` — but the `SCStream` started inside `system` is never
stopped. It keeps capturing (and, worse, keeps its `AVAssetWriter` open
against `system.m4a` in the now-abandoned session folder).

**Fix direction:** wrap `mic.start` in a `do/catch` that calls
`await system.stop()` before rethrowing, or restructure with a `defer` that
stops `system` unless both succeeded.

## P1 — Architecture issues (not urgent, but compounding)

### 1. `AppState` is a god object (674 lines)
[AppState.swift](../../app/Sources/AppState.swift) owns: persisted settings
(UserDefaults get/set scattered via `didSet`), provider/key management,
recording lifecycle, meter/ticker updates at 10Hz, cloud processing
orchestration, offline processing orchestration, import, trash, rename,
post-process invocation, and installing/removing three separate local
runtimes. It forwards `objectWillChange` from five different manager objects
into itself, meaning **any** change in any of those managers re-renders
every view observing `AppState` — including the 10Hz recording ticker's
`micLevel`/`systemLevel` updates, which will thrash the whole SwiftUI tree
while recording.

It also cannot be unit tested in isolation today (it's `@MainActor` in an
executable target with no test target attached to it — the only
`MeetGistKitTests` target tests `MeetGistKit`, not `app/Sources`).

**Suggested split** (do this only after the P0 bugs are fixed and covered by
tests, since this touches almost everything):
- `SettingsStore` — all the UserDefaults-backed `@Published` settings.
- `RecordingController` — start/pause/resume/stop, ticker, meters.
- `ProcessingController` — a real state machine for cloud/offline
  transcription + notes generation (this directly resolves P0 §2, since a
  proper state machine can refuse to start a recording while a job is
  in-flight, or can cancel it explicitly, instead of ad hoc booleans like
  `localNotesTaskActive`).
- `ProviderRegistry` — provider list, key storage, per-provider model
  overrides (currently `effective(_:)`, `hasKey`, `canGenerateMinutes`,
  `setupRequiredStatus` all re-implement provider-capability switches; see
  P1 §2).

### 2. Provider behavior is entirely stringly-typed, duplicated across ~6 call sites
[Provider.swift](../Sources/MeetGistKit/Provider.swift) encodes
`transcribeStyle`/`notesStyle` as free-form strings (`"gemini"`, `"whisper"`,
`"offline"`, `"chat"`, `"apple"`, `"qwen-mlx"`, `"codex-cli"`). Every place
that needs to know "does this provider need a key / is it local / is it
ready" re-implements its own `switch` over these strings:
`AppState.hasKey`, `AppState.canGenerateMinutes`,
`AppState.setupRequiredStatus`, `AppState.generateMinutes`'s error branch,
`Pipelines.make`, `Pipelines.makeNotesWriter`. Adding a new provider style
today means touching ~6 places and hoping none was missed — nothing enforces
consistency, and nothing here is currently caught by a type system.

The offline-provider IDs are also hardcoded as bare strings in three places
in `AppState` (`"offline-qwen3-asr"` appears in `activeOfflineRuntime`,
`activeOfflineCoordinator`, and `offlineConfig`).

**Fix direction:** turn `transcribeStyle`/`notesStyle` into enums, and move
the "does this need a key", "is this local", "readiness check" logic onto
the enum (or onto `Provider` itself) as computed properties/methods, so
there is exactly one place per behavior instead of one per call site.

### 3. Three near-identical runtime managers (~180-250 lines each)
[OfflineRuntimeManager.swift](../Sources/MeetGistKit/OfflineRuntimeManager.swift),
[Qwen3ASRRuntimeManager.swift](../Sources/MeetGistKit/Qwen3ASRRuntimeManager.swift),
and `LocalNotesRuntimeManager.swift` all: install the same pinned CPython
build, verify the same way (SHA-256 check against a hardcoded hash), `pip
install` from a bundled lockfile, `snapshot_download` a HF model, write a
JSON marker file, and expose the same `state`/`installProgress`/
`installDetail` published properties. A `diff` between
`Qwen3ASRRuntimeManager.swift` and `OfflineRuntimeManager.swift` shows the
only real differences are string constants and one model-readiness file
check (`config.json` vs `weights.npz`).

**Fix direction:** extract a single `ManagedPythonRuntime` type parameterized
by a small config struct (python version/build/sha, lockfile resource name,
model repo id + optional revision, readiness marker filename). Each of the
three current managers becomes a thin wrapper (or disappears entirely in
favor of one generic manager instantiated three times) — this also makes it
structurally impossible to forget the revision pin on a new engine (see P2
§2 below, which is exactly this class of mistake already happening once).

### 4. Subprocess supervision (terminate → grace period → SIGKILL, with an optional timeout) is reimplemented ~4 times
`OfflineJobCoordinator.stop(marking:)`, `QwenProcessController` (in
`QwenMLXNotes.swift`), `CodexProcessController` (in `CodexCLINotes.swift`),
and the ad hoc `waitUntilExit()` in `PostProcessRunner` (P0 §4) all
independently solve "make sure a child process actually stops, and don't
hang forever waiting on it." The Codex and Qwen controllers are nearly
identical (`NSLock`-guarded `canceled`/`stop()` with a 2-second
terminate-then-SIGKILL grace period); Codex additionally has a timeout timer
that the others don't but arguably all subprocess call sites need (see P0
§4 — post-process has no timeout at all today).

**Fix direction:** one `ChildProcessController` (terminate/grace/SIGKILL +
optional timeout, pipe draining built in) used everywhere a `Process` is
spawned and needs to be cancellable.

### 5. Everything is polled, nothing is event-driven
`OfflineJobCoordinator`'s monitor loop polls every 400ms
(`OfflineJobCoordinator.swift`, the `monitorTask` in `start(...)`), and
`AppState.processOffline`'s own status-update loop polls the coordinator
every 500ms (`try await Task.sleep(for: .milliseconds(500))` in
[AppState.swift](../../app/Sources/AppState.swift)). This works, but it's an
extra layer of polling on top of polling, and it's the reason
`state(for:)` lookups and `jobs` dictionary rebuilds happen far more often
than they need to. Not urgent, but worth folding into the
`ProcessingController` state-machine refactor in P1 §1 if that work happens.

### 6. Settings persistence has two parallel mechanisms
Most settings are `@Published var x: T { didSet { UserDefaults.standard.set(x,
forKey: Keys.x) } }` pairs declared in `AppState`. But per-provider model
overrides and the Codex reasoning-effort override are raw string-keyed
UserDefaults reads/writes scattered through `effective(_:)`, `setModel`,
`modelOverride`, `setCodexReasoningEffort`, `codexReasoningEffort` — with key
strings like `"model.\(p.id).transcribe"` built ad hoc rather than declared
alongside the `Keys` enum. Cosmetic today, but another spot that will bite
whoever adds the next per-provider setting.

## P2 — Security / supply chain

### 1. Gemini API key travels in the URL query string
[GeminiClient.swift:23](../Sources/MeetGistKit/GeminiClient.swift#L23) (and
again at line 50 for the file-status poll, and in `generate()`):
`URL(string: "\(base)/upload/v1beta/files?key=\(apiKey)")`. Keys in URLs are
more likely to end up in logs, proxies, or crash reports than keys in
headers. Google's Gemini REST API also accepts the key via the
`x-goog-api-key` header — switch to that.

### 2. Qwen3-ASR model download has no pinned revision (unlike its two siblings)
[Qwen3ASRRuntimeManager.swift:106](../Sources/MeetGistKit/Qwen3ASRRuntimeManager.swift#L106):

```python
snapshot_download(repo_id='mlx-community/Qwen3-ASR-1.7B-4bit', local_dir=sys.argv[1])
```

No `revision=` argument, unlike `OfflineRuntimeManager` (pins
`modelRevision` = an exact commit sha) and `LocalNotesRuntimeManager` (same
pattern, per its own doc comment: "Pinned from mlx-community; revision is
the exact commit sha, not a branch, so installs are reproducible"). This
directly contradicts the project's own stated principle
(`AGENTS.md`/`ARCHITECTURE.md`: "Keep model downloads/runtime management
app-owned and explicit") and is exactly the kind of divergence the P1 §3
unification would have prevented structurally.

**Fix:** add `public static let modelRevision = "<pinned commit sha>"` to
`Qwen3ASRRuntimeManager` (look up the current commit for
`mlx-community/Qwen3-ASR-1.7B-4bit` on Hugging Face) and pass
`revision='\(Self.modelRevision)'` into the download script, matching the
other two managers.

### 3. Lockfiles pin versions but not hashes
`Resources/offline-requirements.lock`,
`Resources/offline-requirements-qwen.lock`,
`Resources/qwen-notes-requirements.lock` pin exact package versions (good)
but have no `--hash=` entries, and installs don't pass `--require-hashes`.
An exact version alone doesn't stop a compromised/yanked-and-replaced
release on PyPI from being installed silently. Consider generating hash-pinned
lockfiles (`pip-compile --generate-hashes` or `uv pip compile
--generate-hashes`) and installing with `--require-hashes`.

### 4. `Keychain.set` silently swallows failures
[Keychain.swift](../Sources/MeetGistKit/Keychain.swift): `SecItemAdd(add as
CFDictionary, nil)` — return status is discarded. If saving an API key ever
fails (e.g. Keychain access denied, disk full), the user sees no error and
believes their key was saved; `hasKey` will then report `false` on next
launch with no explanation of why.

## P2 — Testing / CI / observability

1. **No CI actually builds or tests the project.** The only workflow is
   [.github/workflows/cla.yml](../../.github/workflows/cla.yml) (the CLA
   check). There is no macOS CI job running `swift build` / `swift test` /
   the Python test suite. Given `swift test` is currently broken on at least
   one dev machine due to toolchain issues, this would have caught it.
2. **`XCTest` unavailable outside full Xcode** blocks `swift test` entirely
   on this machine — confirm CI (and every contributor's setup) actually has
   Xcode, not just CommandLineTools, or tests are not being run anywhere.
3. Missing test coverage: `SessionRecorder`/`Recorder` (audio capture),
   `MeetingStore.list` (date-parsing, title fallback logic), the cloud
   response parsers in `GeminiClient.swift`/`OpenAIClient.swift`,
   `TranscriptText` helpers, and — most importantly — no tests at all for
   `AppState`'s state machine (P0 §2 would likely have been caught by a test
   like "starting a recording while a cloud process task is active cancels
   it").
4. `tests/MeetGistKitTests/OfflineJobTests.swift` is a 701-line catch-all
   covering offline jobs, Apple notes, Qwen notes, Codex CLI, and meeting
   rename — worth splitting per subsystem as it grows further.
5. Local worker subprocesses (Whisper, Qwen3-ASR) redirect stdout/stderr to
   `/dev/null` ([OfflineJobCoordinator.swift](../Sources/MeetGistKit/OfflineJobCoordinator.swift),
   `workerProcess.standardOutput = FileHandle.nullDevice` /
   `standardError = FileHandle.nullDevice`). If a worker crashes, all that
   survives is an exit code — no log to diagnose why. Consider writing to a
   per-job log file the way `OfflineRuntimeManager.run` and `CodexCLINotes`
   already do for their own subprocess calls.
6. Cloud transcription/notes have no retry/backoff for transient HTTP
   errors (429/5xx) and no per-chunk checkpointing — a long meeting that
   fails on chunk 8 of 10 restarts from scratch, unlike the offline path
   which resumes from committed parts.

## P3 — Minor / polish

- `DateFormatter` used for the session-folder timestamp
  ([SessionRecorder.swift:20](../Sources/MeetGistKit/SessionRecorder.swift#L20))
  has no `locale` set, unlike `MeetingStore`'s `folderNameDateFormatter`
  which explicitly sets `Locale(identifier: "en_US_POSIX")`. On a system set
  to a locale with a non-Gregorian calendar (e.g. Thai Buddhist calendar),
  the stamp `SessionRecorder` writes and the one `MeetingStore` parses back
  could disagree on the year. Add the same POSIX locale here.
- Status strings assigned directly in `AppState` (`"Recording…"`,
  `"Canceled."`, `"Notes ready."`, etc.) bypass `L10n`/`Localization` — they
  never translate even though the rest of the UI does.
- `notesLanguage` defaults to Vietnamese
  (`Prompts.defaultNotesLanguage`), but the UI's `Localization`/`Lang` enum
  only supports `en`/`zh`/`system` — worth confirming this default is
  intentional or should be reconciled with the supported UI languages.
- Custom provider IDs are generated as
  `"custom-\(customProviders.count + 1)-\(UInt8.random(in: 0...255))"`
  (`AppState.addCustomProvider`) — a collision is unlikely but possible
  (256 buckets); prefer a UUID.

## Suggested execution plan for the next agent

1. P0 §1–§6, each as an independent, narrowly-scoped commit with a
   regression test where feasible (offline job tests already establish the
   pattern — e.g. `testConfirmedResetDeletesOnlyGeneratedTranscriptionArtifacts`,
   `testWorkerThatIgnoresTerminationIsForceStopped` — follow that style).
2. P2 security fixes (§1–§4 under "Security / supply chain") — small,
   independent, low-risk.
3. Add a macOS GitHub Actions workflow running `swift build`, `swift test`,
   and the Python test suite (`pip install -r scripts/requirements.txt &&
   pytest tests`), gated on the runner actually having full Xcode installed
   (`xcode-select -p` should point under `/Applications/Xcode.app`, not
   CommandLineTools — verify this in the workflow before trusting green CI).
4. Only after 1–3 are merged and covered by CI: the P1 refactors (split
   AppState, de-stringify providers, unify runtime managers, unify
   subprocess supervision). These touch a lot of surface area and are much
   safer with the P0 bugs already fixed and tests already passing in CI.
